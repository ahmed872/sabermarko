## 1. ما الذي تغيّر
| الجزء | التغيير |
|---|---|
| الدفعات | كل استلام = دفعة مستقلة (كمية، تكلفة شراء، صلاحية، مورد، سطر الشراء، تاريخ الاستلام). لا دمج أبدًا. التحويل بين الأماكن ينشئ دفعة تحتفظ بأصلها ومورّدها. |
| البيع | يستهلك الدفعات **الصالحة فقط** بالأقرب انتهاءً (FEFO). كمية منتهية لا تُباع أبدًا، حتى لو كان «البيع بالسالب» مفعّلًا. |
| مرتجع المورد | مرتبط بدفعة محددة، ذري (Atomic)، مع كل القيود المطلوبة. |
| شاشة الصلاحية | 4 مستويات قابلة للضبط + تفاصيل كل دفعة + «إرجاع للمورد» و«إعدام». |
| التنبيهات | في الرئيسية لكل مستوى، مثال حرفي: «⚠️ يوجد 24 قطعة من لبن X ستنتهي خلال 18 يومًا.» |
| العروض الذكية | لا عرض ولا هدية من كمية منتهية؛ لا عرض بعد الصلاحية (مفروض عند الاعتماد)؛ اقتراح الإرجاع للمورد كبديل. |
| قاعدة البيانات | الإصدار v3 (أعمدة نسب الدفعة) مع ترقية تلقائية من v1/v2 دون فقد بيانات. |
| شاشة الشراء | حقل رقم الدفعة بجوار تاريخ الصلاحية (التحويل «10 × 12 = 120 قطعة» والمورد والتكلفة موجودة من قبل). |
| الإصدار | 1.1.0. |

## 2. تصميم الدفعات والصلاحية
- جدول `batches`: `qty`, `initial_qty`, `unit_cost` (تكلفة القطعة لهذه الدفعة)، `expiry_date`, `batch_no`, `received_at`, `supplier_id`, `purchase_item_id`, `source_batch_id`, `ref_type/ref_id`.
- مثال لبن X: 10 كراتين × 12 بتكلفة 200 وصلاحية 2027-01-15 ← دفعة 120 قطعة بتكلفة 16.67 للقطعة. شراء ثانٍ 5 كراتين × 220 وصلاحية 2027-04-20 ← دفعة ثانية مستقلة. حتى شراء ثالث **بنفس تاريخ الصلاحية** يبقى دفعة منفصلة.
- **التكلفة التاريخية:** تكلفة كل سطر بيع محفوظة لحظة البيع (لا تتغير بشراء لاحق أو مرتجع — مختبر). المخزون يُقيَّم بمتوسط التكلفة المرجح كما في النظام، وقيمة كل دفعة تُعرض بتكلفتها هي.
- **منتهي الصلاحية** = بعد يوم تاريخ الصلاحية (يجوز البيع في يوم الصلاحية نفسه).
- `sellableStock()` في المحرك يحسب: الصالح للبيع، والمنتهي، والكمية الأقدم من تتبع الدفعات.

## 3. مسار مرتجع المورد
تنبيه ← شاشة الصلاحية (المستوى، الكمية، التكلفة، القيمة، المورد، الأيام المتبقية، سرعة البيع، الإجراء المقترح) ← «إرجاع للمورد» ← المورد (من الدفعة) + الكمية + السبب
(قرب انتهاء الصلاحية / منتهي الصلاحية / تالف من المصدر / خطأ في التوريد / أخرى) + خصم من الحساب أو استرداد نقدي ← مرتجع شراء حقيقي.

قواعد مفروضة داخل المحرك: لا أكثر من كمية الدفعة؛ دفعة غير موجودة أو لمنتج/مكان آخر ← رفض؛ مورد غير مورد الدفعة ← رفض؛ لا مخزون سالب؛
الخصم من نفس الدفعة؛ حركة مخزون + مرتجع شراء + رصيد المورد + سجل التدقيق في **معاملة واحدة** (أي خطأ في أي سطر يلغي الكل — مختبر).
بدون سعر يُحسب المرتجع بتكلفة شراء الدفعة نفسها (حتى أمين المخزن الذي لا يرى التكلفة يرجع بقيمة صحيحة).

## 4. تنبيهات الصلاحية
| المستوى | الافتراضي | الإعداد |
|---|---|---|
| منتهي | بعد تاريخ الصلاحية | — |
| قريب جدًا | ≤ 7 أيام | `inventory.expiryCriticalDays` |
| قريب | ≤ 30 يومًا | `inventory.expiryAlertDays` |
| متابعة | ≤ 90 يومًا (الشاشة فقط) | `inventory.expiryWatchDays` |

## 5. حماية المخزون المنتهي
- داخل `issueStock(... sellableOnly)` المستخدمة في كل بيع، وفي حساب السلة (تظهر الرسالة فور إضافة الصنف):
  «لا يمكن بيع "لبن X": الكمية الصالحة للبيع 50 فقط، ويوجد 120 منتهية الصلاحية لا يجوز بيعها. سجّلها كتالف أو أرجعها للمورد.»
- مختبر للمالك وللكاشير، ومع «البيع بالسالب» مفعّلًا، والعملية لا تترك أثرًا.
- المحاكاة السنوية: **0** سطر بيع أُخذ من دفعة منتهية (فحص المدقق المستقل على 132,674 سطرًا).

## 6. تغييرات العروض الذكية
- الهدف والهدية من **المخزون الصالح فقط**؛ منتج مخزونه كله منتهٍ لا يُقترح عليه عرض ولا يُستخدم هدية.
- مدة أي عرض ≤ آخر يوم يمكن فيه بيع البضاعة؛ عروض الأزواج/الكمية تُلغى إذا كان الوقت المتبقي < 3 أيام، والباقات < 7.
- **عند الاعتماد** (في المحرك): عرض ينتهي بعد صلاحية المنتج أو الهدية ← رفض `PROMO_PAST_EXPIRY`.
- عرض الصلاحية يذكر «بديل: راجع إرجاع الكمية للمورد …» عندما يكون مورد الدفعة معروفًا.
- لا شيء يُنفَّذ تلقائيًا: البرنامج يقترح والمالك يقرر.

## 16. المخاطر المعروفة المتبقية
1. التشغيل الفعلي والطباعة على Windows لم يُختبرا يدويًا بعد (أعلاه).
2. المُثبّت غير موقّع ← تحذير SmartScreen (قرارك بعدم شراء شهادة).
3. تحديد «منتهي» بتاريخ الجهاز: جهاز بتاريخ خاطئ يغيّر الحكم (حماية الترخيص ترصد إرجاع الساعة للخلف، لا تقديمها).
4. المخزون الأقدم من تفعيل تتبع الصلاحية (بلا دفعات) يُعامل كصالح لعدم معرفة تاريخه.
5. فاعلية العروض الذكية تحتاج بيانات محل حقيقي للحكم عليها.
6. حماية الفترة التجريبية لا تصمد أمام هندسة عكسية محترفة (طبيعي لبرنامج يعمل بدون إنترنت).

## 17. ما تفعله على جهاز Windows
1. افتح رابط الـartifact أعلاه وأنت مسجّل في GitHub ← أسفل الصفحة **Artifacts** ← `windows-installer` ← فك الضغط.
2. PowerShell: `Get-FileHash .\SaberMarko-POS-Setup-1.1.0.exe` ← يطابق `SHA256SUMS.txt` والقيمة أعلاه.
3. شغّل المُثبّت ← «Windows protected your PC» ← **More info** ← **Run anyway**.
4. نفّذ قائمة `docs/RELEASE.md` بندًا بندًا، وأرسل لي النتيجة وصور أي مشكلة (خصوصًا الطباعة).
5. **الإصدار الرسمي (بنفسك، عند الاستعداد للبيع):**
   1. على جهازك: `npm run license:keygen` ← يحفظ المفتاح الخاص **خارج المشروع** ويكتب المفتاح العام في `src/main/license/public-key.ts`.
   2. `git add src/main/license/public-key.ts && git commit -m "Production license key"` ثم `git push`.
   3. `git tag v1.1.0 && git push origin v1.1.0`.
   4. GitHub Actions يبني المُثبّت ويتحقق منه تلقائيًا ثم ينشر **GitHub Release** فيه `SaberMarko-POS-Setup-1.1.0.exe` و`SHA256SUMS.txt` — رابط دائم لا ينتهي بعد 30 يومًا. إذا كان المفتاح التجريبي ما زال موجودًا يرفض البناء النشر (حماية مقصودة).
